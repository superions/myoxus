# Database collaboration and recovery

[Documentation](../../../README.md) / [Operations](../../README.md) / [Data operations](../README.md) / [Database operations](./README.md)

Diagnose database collaboration, view, row-content and notification incidents while preserving the current workspace data.

## Moving Workspace Tasks into a Project

Use Move to Project in existing Task details. Preview lists the explicit
selection, current destination, graph boundaries and new display-ID allocation.
Related Tasks require explicit selection expansion; recoverable Trash or
external references may require normal link repair before retry. Cancel writes
nothing. The server rechecks permissions and all native revision/owner fences
under one transaction, preserving Row UUIDs and contents.

After an unknown outcome, use Check current location and reopen the original
Row. Do not recreate/replay it or force a stale source-owner edit. Old links and
capture recovery resolve the same authorized Task within its workspace. Warm
client state grants no access after terminal denial. Reminder UUIDs/owners and
due semantics remain native: eligible pending schedules receive fresh
generations, old queued claims become invalid, and fired/cancelled/closed rules
remain terminal. Historical activity and capture facts retain their original
scope; movement does not synthesize assignment/completion/creation notices.

## Live collaboration runtime

Database writes use optimistic `edit_revision` preconditions. A stale client
receives a `MIX_DATABASE_*_CONFLICT` with current server state; this is an
expected concurrency result, not an API outage. The Web client asks the user to
load the latest value or explicitly force the same attempted mutation. Forced
writes remain visible in operator audit and workspace activity.

Row-content create, attach and detach intentionally do not support force retry.
After a conflict the client loads the latest Row instead of replaying an action
that could duplicate a page or replace a newer association.

Presence and committed-change delivery use the existing Socket.IO endpoint and
Redis fanout. In a multi-API deployment, all instances must use the same Redis
configuration. Presence is ephemeral and pruned after disconnect/staleness;
there is no presence table to repair. A failed mutation must not publish
`database:change`, while a committed mutation must reach users connected to a
different API instance.

Server-authored Row-content creation also publishes normal document-sync
events. The leaf Yjs update is persisted and broadcast before the workspace-root
`meta.pages` registration, through both supported sync protocol rooms and the
Redis adapter. If a newly created page appears in the Row projection but does
not mount in an already open browser, inspect both document broadcasts and
Redis fanout.

## Workspace Automation recovery

Workspace Automations now advance through the API-owned PostgreSQL/Glirulus
worker. Redis still handles existing intake/delivery paths, but it is not the
execution receipt or a prerequisite for durable retry admission. Check the
native run list, safe error code and runtime readiness before treating queue
health as the sole explanation for a stalled run.

The runtime uses the ordinary Myoxus migration ledger, including migration
`1053`, and the existing PostgreSQL pool/TLS settings. Do not run Glirulus's
standalone migrations or manually edit engine claims, frozen inputs or result
receipts. The registry fork retains existing `sayiir_workflow_*` SQL objects and
the `sayiir_task_ready` channel; their names do not require data repair. A runtime/schema mismatch fails readiness. One unavailable accepted
definition is reported as `MIX_AUTOMATION_INPUTS_UNAVAILABLE` without blocking
other eligible runs; retain its input and restore the matching implementation
before retrying. Malformed or unsupported accepted inputs require inspection,
not reconstruction from the latest rule.

After an interruption or unknown response, inspect the existing native run and
result first. Retry through the existing authorized command retains the run,
accepted inputs and effect identities; PostgreSQL atomically admits the retry
and engine snapshot. It must not recreate deleted results or replay a committed
write over manual changes. A retired claim cannot authorize a native effect:
the writer checks current rights, target scope and owner/generation in the same
transaction as the effect ACK. The server handles expired-claim recovery and
bounded shutdown; no separate workflow service is needed.

Native Task notifications and workflow signals remain separate delivery facts.
Notification intents retain their existing per-recipient Inbox idempotency and
retention. Review/handover invalidation and prerequisite facts stay synchronous
with the native Task write; only committed signal delivery reaches Glirulus.
An outbox acknowledgement is recorded after correlated delivery, and engine
checkpoints do not substitute for native decision, content/capture or effect
receipts. Diagnose these owners rather than replaying an ordinary Task edit as
an approval or introducing a second signal-delivery path.

Webhook receivers must deduplicate the stable `x-myoxus-delivery` action ID.
Signed retries retain that identity, but receiver-side exactly-once effects
cannot be guaranteed. Native writers retain business authorization and receipts;
the engine advances only the accepted workflow.

Document reviews use the same native run and recovery controls. Reopen the
assigned review Task to read its current status, original document and any
follow-up. Only its confirmed, still-authorized reviewer can Approve or Request
changes; marking the Task Done through an ordinary editor is not approval.
Reassignment, cancellation, movement or deletion ends an undecided review in
Needs attention. A changed source revision also prevents a stale decision or
follow-up; do not overwrite the document to make an old request applicable.

After an unknown decision response, check the same Task before retrying the
confirmed decision. Its native receipt, Task completion and signal intent are
one transaction, so a timely accepted decision remains valid after delayed
delivery or restart past the deadline. Ordinary Task Due edits do not extend
that deadline. Retry preserves identities and never recreates a deleted result;
a stale or expired request needs a new explicit review. Stop retains committed
Tasks and documents. Do not manually inject engine events or edit decision
receipts to resume a run.

Prerequisite handovers use the same Tasks/context run inventory. Reopen the run
to inspect prerequisite progress, Stop or open its existing result and source.
No waiting Task is created. Already-complete prerequisites count, and later Task
completions can arrive in any order across a restart. The accepted deadline is
separate from Task Due; delayed dispatch does not discard a timely committed
completion. Reopened, cancelled, moved, deleted or unavailable prerequisites
require attention and cannot create a handover. Retain the existing request and
result identities after an uncertain response; do not inject signals or edit
completion facts to force continuation.

## Task correction and preparation recovery

Inspect Task content from its existing context. Review the actual Field changes
before confirming. Apply belongs to that exact proposal; a conflicting edit
requires fresh preparation. Decline changes no Task values. Reopen the same run
to check a lost response or its accepted outcome; do not create another request
or force stale proposed values. Correction confirmation is separate from document
approval and creates no review Task.

In the existing automation settings, personally enable a reviewed preparation
recipe or maintenance of explicitly selected Tasks. Automatic mode alone enables
nothing. Maintenance reacts to your changes on those selected Tasks, then waits
for a separate correction decision. Task-created preparation creates at most one
native content document for the run/Task and preserves any existing content.
Refresh the rule's timeline and check the same run, including dead-letter runs.
Maintenance reopens its frozen correction review. Preparation shows its actual
result document and the currently permitted Retry/Stop controls. Retrying a
failed preparation preserves its Run and reserved result; it does not create
another Task or replace existing content.

Disable the personal rule or downgrade assistance to fence pending and future
automatic work. Saved choices and committed documents remain; returning to
Automatic does not resurrect invalidated runs. A moved Task keeps its identity,
content and native reminders. Old-container assistance cannot write there, and
the destination needs its own explicit opt-in. An unavailable/retired offering
needs a fresh source/configuration review, not manual repair of stored receipts.
